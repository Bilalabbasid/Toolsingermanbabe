# CoolWave all-tools audit — 15 September 2026

## Scope and evidence

This is an audit and repair plan, **not a certification that every conversion works**. The public registry exposes 165 distinct active/beta tool pages: 128 literal definitions in `src/config/tools.config.ts`, 24 text/developer utilities in `src/config/utilities.config.ts`, and 13 media/archive tools in `src/config/media_archive.config.ts`. The two supplemental arrays are spread into the main registry twice and then deduplicated by slug. Every registered `processingEngine` has a dispatcher case, but some cases route multiple slugs to an unrelated default behavior. I reviewed the registry, `ToolDispatcher`, 30 client engines, seven server adapters, shared upload/job/storage code, and the built local server on port 3112. This is source review plus representative functional tests; it is **not** 165 individual end-to-end conversions.

`npm run typecheck` passed, `npm run build` passed and generated 165 tool routes, and `npm test` passed 33 tests with two skipped. Those tests cover only a small part of the tool matrix. The reported image-only résumé has zero selectable PDF text. Scanned-PDF Word has already been changed in the workspace, before the user's instruction to stop fixing: it now defaults to embedding the original page image, offers OCR text as an explicit alternative, and omits the filename heading. Four focused regression tests pass. The production build also completed the layout-mode job and downloaded a 449,060-byte DOCX containing the page image. Visual page rendering remains **unverified**: the bundled `render_docx.py` could not run because `soffice.exe` is absent on this Windows host. No further application code fixes were made during this audit.

Functional checks on the isolated production build:

- The reported scan submitted to `office_pdf_to_xlsx` failed at 80% with `Cannot read properties of null (reading 'forEach')`. The API displayed that raw internal exception in the job status.
- The reported scan submitted to `office_pdf_to_docx` with `scanMode=layout` completed and its download succeeded. This verifies transport and DOCX packaging, not Word's visual pagination.
- The same scan submitted to `office_pdf_to_pptx` completed and downloaded a valid one-slide PPTX, but it contained **zero image files and no extracted scan text**. This is a false success: the résumé was lost.
- A valid UTF-8 TXT containing German text, a euro sign, and a checkmark submitted to `office_txt_to_pdf` failed with `WinAnsi cannot encode "☑"`. A UTF-8 BOM caused a separate failure. Both raw exceptions appeared in job status.
- `/de/pdf-in-excel-umwandeln` returned HTTP 200 from the production build. A responding page does not prove that its transformation works.

Severity: **C** critical (security or substantial irreversible data loss), **H** high (invalid/empty download, incorrect document, severe misleading claim, or common input failure), **M** medium (partial functionality, confusing behavior, or edge-case failure). `Confirmed` means reproduced with a file or directly established by the implementation; `Risk` needs a dedicated regression before asserting the user-visible outcome.
